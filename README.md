# KBO 실시간 승률 예측 · 설명 시스템

> 경기 시작부터 종료까지 **투구 하나하나의 상황을 수집**해 그 시점의 승률을 계산하고,
> **왜 그 숫자가 나왔는지**와 **어디서 흐름이 바뀌었는지**를 함께 보여준다.

> **데이터 이용에 관하여**
> 네이버 스포츠의 **인증 없는 공개 GET 엔드포인트**만 사용한다. 로그인·토큰·우회 없음.
> 요청은 `config.REQUEST_DELAY` 로 **초당 2.5회**로 제한되며, 워커를 늘려도 총 요청량은 고정이다.
> **개인 학습·포트폴리오 목적**이며, 데이터 저작권은 네이버 및 KBO에 있으므로
> 수집한 원본 데이터는 이 저장소에 포함하지 않는다 (코드만 공개).

## 1. 기존 프로젝트에서 무엇이 달라졌나

| | [KIA_VS_SAMSUNG](https://github.com/geonwoong-lee/KIA_VS_SAMSUNG) | [KBO_Data_Analysis](https://github.com/geonwoong-lee/KBO_Data_Analysis) | **이 프로젝트** |
|---|---|---|---|
| 예측 단위 | 시리즈 1건 | 선수 시즌 OPS | **투구 1개 = 1행** |
| 데이터 | 엑셀 수기 입력 | Kaggle 정적 CSV | **네이버 문자중계 API 자동 수집** |
| 시점 | 경기 전 | 시즌 후 | **경기 중 실시간** |
| 표본 | 16경기 | 선수×시즌 | **1,136경기 · 632,935 이벤트** |
| 검증 | 정답률 66.7% | R² | **Log loss · Brier · 보정 곡선 + 베이스라인 3종 + 네이버 대비** |
| 설명 | 없음 | Feature importance | **WPA · SHAP · 반사실 · 레버리지 · 흐름 전환점** |

기존 두 레포의 근본 한계는 **표본이 16경기**였다는 점이다. 16경기로 얻은 정답률 66.7%는
동전 던지기와 통계적으로 구분되지 않는다. 이 프로젝트는 같은 야구 데이터를
**상태(state) 단위로 재정의**하고, 평가지표를 정답률에서 **확률의 정확도**로 바꾼다.

**읽는 법**

- **네이버에는 두 방식 모두에서 졌다** (+2.4% / +1.1%). 이게 현재의 정직한 위치다.
- 네이버 비교 구간은 `naver_wp` 가 0·100이 아닌 행만 쓴다. **이미 승부가 갈린 쉬운 행이 빠져**
  전체보다 log loss 가 높게 나온다. 같은 행끼리 비교했으므로 공정하다.
- 폴드별 log loss 는 0.414~0.481. 절대값에는 ±0.02 수준의 불확실성이 있지만,
  **베이스라인을 동일한 OOF 행에서 평가**했으므로 비교 자체는 정밀하다.

> 개발 도중 한때 "네이버를 이겼다"는 수치가 나왔다. 그건 파서 버그로 인해
> 모델이 **경기 식별자를 외운 결과**였다(§5 ④). 버그를 고치자 사라졌다.

동점·무사·주자없음이라는 동일 국면에서 초 → 말 전환 시 홈팀 승률 상승폭:

| 이닝 | 모델 | 실제 |
|---|---|---|
| 2회 | +4.0%p | +3.8%p |
| 3회 | +6.3%p | +6.2%p |

후반으로 갈수록 효과가 커지는 것도 야구적으로 맞다. §5 ④ 이전에는 모델이 +9%p,
실제가 +5%p로 **2배 과대평가**했다.

## 3. 데이터 — 네이버 스포츠 문자중계

`api-gw.sports.naver.com` 의 공개 GET 엔드포인트. 인증 불필요, HTML 파싱 없음.

| 엔드포인트 | 내용 |
|---|---|
| `/schedule/games` | 일정 · 결과 · 경기 상태 |
| `/schedule/games/{gameId}/relay?inning=N` | **이닝별 문자중계 (투구 단위)** |
| `/schedule/games/{gameId}/preview` | 선발투수 · 라인업 · 팀 순위 |

`gameId` 형식: `20260823HTWO02026` = 날짜 + 원정팀 + 홈팀 + 더블헤더플래그 + 시즌

한 경기가 평균 **557개 이벤트**를 만들고, 그중 절반 이상이 투구 단위다.
**모든 이벤트에 그 시점의 완전한 게임 상태가 붙어 있다.**

```json
"currentGameState": {
  "homeScore":"0","awayScore":"0","out":"2","ball":"0","strike":"0",
  "base1":"5","base2":"3","base3":"2",          // 0=비어있음, 그 외=주자의 타순 번호
  "pitcher":"54640","batter":"53312"
},
"speed":"146", "stuff":"투심", "pitchResult":"B"   // 구속·구종·투구 결과
```

### 문서 없는 API에서 실측으로 알아낸 것

1. **`textRelays` 는 이닝 안에서 최신순으로 내려온다.** 그대로 쓰면 시간이 거꾸로 흐른다.
   정렬 키는 `(textRelay.no, textOption.seqno)`.
2. **`base1/2/3` 은 0/1 플래그가 아니라 주자의 타순 번호다.** `base1:"5"` = 5번타자가 1루.
3. **`currentGameState` 는 이벤트 *직후* 상태다.** 삼진 이벤트의 `out` 은 이미 증가해 있다.
4. **`textRelay.metricOption` 에 네이버 자체 승률이 타석 단위로 있다.**
   → **직접 비교 벤치마크**로 쓴다 (특성으로는 절대 쓰지 않는다).
5. **`currentPlayersInfo` 는 이벤트마다 바뀌지 않는다.** 응답 전체에 고정된 한 쌍이다.
   여기서 선수 성적을 뽑으면 **경기 내 상수**가 된다 → §5 ④
6. 선수 성적의 올바른 출처는 **`batterRecord.seasonHra`** (타자)와
   **`home/awayLineup.pitcher[].seasonEra`** (투수)다.
7. **`batterRecord.vsHra`(상대 전적)는 홈팀 타자만 계산된다.** 원정은 전원 `0.000` → §5 ⑤
8. 일정 조회 API는 한 번에 약 310경기까지만 응답 → 월 단위로 쪼개서 호출.

```bash
python -m src.collect --season 2026 --workers 3
```

- 수집한 `game_id` 는 체크포인트에 남아 중단 후 이어받는다. 40경기마다 샤드로 저장.
- **수집기 동시 실행은 잠금 파일로 막는다.** 두 프로세스가 같이 돌면 체크포인트를
  서로 덮어써 실제로 157경기가 사라졌다.
- 전송 실패는 `TransientError` 로 '데이터 없음'과 구분한다. 구분하지 않으면
  DNS 블립 한 번에 **6회가 통째로 빠진 경기가 정상인 척 저장된다** (실제로 4건 발생).
- 이닝 번호에 구멍이 있으면 저장을 거부한다. 단, 종료 이닝은 일정 API의
  `statusInfo` 와 비교한다 — **강우 콜드게임이 실재**하기 때문이다.

## 4. 모델 설계

> 경기 중 임의의 시점 *t* 의 상태 **s** 에서, 홈팀이 최종 승리할 확률 P(홈 승 | s)

- **1행 = 게임의 한 상태**, **라벨 = 그 경기의 최종 홈팀 승패** (무승부 제외)
- 3아웃 행은 '다음 반이닝 시작(무사·주자없음)'으로 정규화 → 같은 국면은 항상 같은 특성 벡터

### 특성 14개 — 절제 실험으로 확정

| 묶음 | 특성 |
|---|---|
| 점수 × 시간 | `score_diff` `score_x_progress` `score_per_out_left` `outs_left_bat` `outs_left_field` `is_bottom` |
| 주자 · 카운트 | `base_state`(0~7) `re24` `run_potential` `outs` `balls` `strikes` `is_walkoff_chance` `is_last_at_bat` |

**`outs_left_bat` / `outs_left_field`** — 야구 승률의 가장 강한 구조적 신호.
3점 차는 1회에는 별것 아니지만 9회에는 사실상 끝이다. 이 차이는 "이닝"이 아니라
**"각 팀에게 남은 공격 아웃 수"** 로 표현된다.

**`score_per_out_left`** — 위 논리를 한 값으로 압축. 점수차 ÷ 남은 총 아웃.
모델 gain 의 **66.8%** 를 차지한다.

**`re24`** — 24개 베이스-아웃 상태별 잔여 득점기대값. **학습 경기에서만** 추정한다.

### 누수 차단

| 함정 | 대응 |
|---|---|
| 경기 내 누수 — 같은 경기의 1회와 9회가 train/test로 나뉘면 라벨이 샌다 | 분할은 **항상 경기 단위** (`GroupKFold` on `game_id`) |
| 미래 정보 누수 | 라벨 외에는 "그 시점까지의 누적"만 사용 |
| RE24 누수 | 학습 경기에서만 추정 |
| 벤치마크 오염 | `naver_wp_home` 은 평가 전용, `FEATURES` 에서 제외 |
| 투수 ERA 누수 | 라인업에 **처음 등장했을 때** 값을 쓴다. 마지막 이닝 값을 쓰면 그날 얻어맞은 결과가 ERA에 반영된다 |

### 학습

LightGBM(binary) + 점수 관련 특성에 **단조 증가 제약**.
점수차가 커지는데 승률이 떨어지는 구간이 생기면 그건 모델이 아니라 버그다.

조기종료 라운드 수와 확률 보정기는 모두 **학습 경기 내부 GroupKFold(5-fold) OOF 예측**으로
결정한다. 별도 검증 홀드아웃을 두지 않는 이유는 §5 ③에 있다.

## 5. 실측으로 배운 것

이 프로젝트에서 가장 값진 결과는 성능 수치가 아니라 아래 다섯 개다.

①~③은 하나의 사실에서 나온다 — **유효 표본은 행 수가 아니라 경기 수다.**
한 경기는 550여 행을 만들지만 그 행들은 **모두 같은 라벨**을 공유한다.
행이 60만 개여도 독립 표본은 경기 수(1,136개)뿐이다.

### ① 모델이 야구가 아니라 "어느 팀 경기인지"를 외웠다

첫 학습에서 LightGBM(0.4162)이 **파라미터 4개짜리 로지스틱 회귀(0.3984)에 졌다.**
경기 내내 변하지 않는 사전정보(선발 ERA 차, 팀 승률 차) 두 개가 gain 의 **38.6%** 를 먹고 있었다.
183경기라면 그 조합은 곧 **경기 식별자**다.

**대응** — 사전정보를 비활성화하고 국면에서 유도되는 상호작용을 넣었다. 0.4162 → **0.3981**.

### ② 용량은 병목이 아니었다 — 가설이 틀린 걸 확인한 것도 소득

규제를 세게 걸자 주자·카운트의 gain 이 0.5%까지 떨어져 하이퍼파라미터를 탐색했다.
**6개 설정이 0.0014 폭 안에 다 들어왔다.** 튜닝을 접고 병목이 있는 곳(특성)으로 옮겼다.

### ③ 검증 점수가 가장 좋은 보정기가 테스트에서 가장 나빴다

| 시도 | isotonic 검증 | isotonic 테스트 | 무보정 테스트 |
|---|---|---|---|
| 홀드아웃 52경기 | **0.4990** (1위) | 0.4401 | **0.4102** |
| OOF 320경기 | **0.4552** (1위) | 0.4948 | **0.4917** |

isotonic 은 계단 함수다. 실측하니 **9,973개 예측값을 50단계로 뭉갰다.**
정확도만 망가지는 게 아니다 — **WPA 는 승률의 차분**이라, 보정기의 계단이 그대로
'승부처'로 잘못 잡힌다. 4회 동점의 평범한 3루수 땅볼 아웃에 **WPA +36.9%p** 가 찍혔고,
같은 값이 한 경기에 네 번 반복된 것이 결정적 단서였다.

**대응** — `src/calibrate.py` 에서 정확도만으로 고르지 않는다. 후보를 모두 학습해
**OOF log loss 와 함께 고유 출력값 개수(계단 수)를 같이 기록**하고,
isotonic 은 검증 경기 1,000개 이상 + Platt 대비 0.01 이상 개선일 때만 채택한다.

### ④ 같은 컬럼이 반이닝마다 정반대로 작용했다

`pitcher_season_era` 는 "지금 던지는 투수의 ERA"인데, **초에는 홈 투수, 말에는 원정 투수**다.
같은 컬럼이 반이닝마다 라벨에 반대로 작용한다.

증상: 동점·무사·주자없음에서 모델의 초→말 상승폭이 +9%p, 실제는 +5%p — **2배 과대평가**.

**대응** — 선수 특성을 전부 "홈팀에게 유리한 방향이 +"로 부호 고정.
부수 효과로 단조 증가 제약을 걸 수 있게 됐다.

그런데 여기서 더 깊은 버그가 드러났다. 3아웃 정규화 행은 상태가 다음 반이닝으로
넘어가는데 **선수 데이터는 직전 반이닝 것 그대로**라, 부호만 뒤집혀
2-2 동점에서 **4회말 33.3% → 5회초 58.6% (+25%p)** 라는 점프가 생겼다.
`bat_adv_home` 하나가 −16.3%p → +12.8%p 로 혼자 29%p를 흔들었다.

**대응** — 부호는 `disp_is_bottom`(선수 데이터가 실제로 속한 반이닝)으로 정한다. 점프 25.2 → 12.1%p.

### ⑤ 선수 정보는 승률에 기여하지 않는다 — 세 번 확인했다

처음엔 선수 특성이 가장 값진 줄 알았다. 빼면 **+0.0116** 으로 손실이 제일 컸다.
그런데 그 값이 전부 버그의 산물이었다.

**1차 — 투수 ERA · 타자 타율.** `currentPlayersInfo` 가 이벤트마다 바뀌지 않는 필드라,
두 값이 **경기 내 상수**로 들어가 있었다. §① 의 재발이다. 실측 증거:

| 타자 | 진짜 시즌 타율 | 모델이 본 값 |
|---|---|---|
| 서건창 | 0.319 | 0.100 |
| 박주홍 | 0.231 | 0.100 |
| 권혁빈 | 0.222 | 0.100 |

올바른 출처(`batterRecord.seasonHra`, 라인업 `seasonEra`)로 고쳐 다시 재니 **기여가 0** 이었다.

**2차 — 상대 전적(vsHra).** 타자의 '이 투수 상대 타율'이 API에 있다. 그런데
**홈팀 타자만 계산된다.** 원정 타자는 전원 `0.000`:

```
ha=0(원정) 김도영    vsHra='0.000'   seasonHra=0.302
ha=1(홈)  김건희    vsHra='0.351'   seasonHra=0.275
```

이대로 넣으면 "말에만 값이 있는" 특성이 되어 **또 `is_bottom` 을 인코딩한다.**
게다가 표본이 통산 8타수 수준이라(`pitcherVsBatterCareerStats`) 표준오차가 ±0.16이다. 사용 불가.

**3차 — 좌우 매치업.** 좌우는 **양 팀 모두** 제공되고, 선수 고정 속성이라 경기 상수도 아니며,
표본이 타자당 수백 타석이다. 조회표를 만들어(`src/handedness.py`, 424명) 붙였다.
매칭 실패 0%, 좌우 분포도 균형(−1: 197,498행 / +1: 191,534행).

| 특성 세트 | 개수 | OOF log loss |
|---|---|---|
| 현재 | 14 | **0.4479** |
| + 좌우 매치업 | 15 | **0.4479** |
| + 좌우 + 시즌성적 | 17 | **0.4479** |
| + 시즌성적만 | 16 | **0.4479** |

**소수점 넷째 자리까지 완전히 같다. 데이터가 완벽한데도 0이다.**

**왜 그런가** — 좌우 매치업은 *타석 결과*에는 분명히 영향이 있다(리그 평균 타율 2~3푼 차).
하지만 우리가 예측하는 건 **경기 최종 승패**다. 지금 타석의 기대값이 2푼 오르내려도
남은 20~40타석에서 좌우가 뒤섞이며 평균으로 씻겨나가고, 감독이 대타·불펜으로
이미 최적화하고 있어 잔여 효과는 더 작다.

**결론** — 특성을 24 → 19 → **14개**로 줄이는 동안 성능은 계속 좋아졌다.
경기 중 승률은 **점수와 남은 아웃이 지배**하며, 개별 선수 정보는 희석된다.

## 6. 설명 — 왜 이 승률인가, 어디서 흐름이 바뀌었나

### ① WPA — "방금 그 플레이가 승률을 얼마나 바꿨나"

승률의 **차분**. 야구계가 이미 쓰는 언어이고 모델과 독립적으로 정의되므로 가장 신뢰받는다.

### ② SHAP — "지금 이 승률은 어떤 요인이 만들었나"

LightGBM 내장 TreeSHAP 을 쓰되 **로그오즈가 아니라 %p 단위로 변환**해,
각 항의 합이 정확히 `(예측확률 − 기준확률)` 이 되게 했다.

### ③ 반사실 — "만약 무사였다면?"

상태를 **하나만** 바꿔 다시 예측한다. 파생 특성은 `add_derived()` 로 반드시 재계산한다.

### ④ 레버리지 — "이 타석이 승부를 흔들 폭"

다음 타석 결과(아웃/볼넷/단타/2루타/홈런)에 리그 평균 발생확률을 가중한 기대 변동폭.
평균 타석의 몇 배인지로 표시한다. **불펜 투입·대타 타이밍에 직접 쓰이는 지표다.**

### ⑤ 회별 승률 추이 — x축이 '회(초/말)'다

이벤트 번호를 x축에 쓰면 1회가 40칸, 5회가 15칸을 차지해 야구적 의미가 없다.
반이닝 단위로 요약하면 한 경기가 18~20행이 되고 각 행이 실제 야구 단위와 1:1 대응한다.
종료 승률을 '다음 반이닝의 시작 승률'로 정의해 **변화량의 합이 경기 전체 변화와 정확히 일치**한다.

### ⑥ 흐름 전환점 — |WPA| 상위와는 다른 것

8-1 상황의 홈런은 WPA 가 커도 흐름을 바꾸지 않는다. 이미 결정된 경기다.
그래서 승률을 다섯 구간(홈 결정적 / 홈 우세 / 접전 / 원정 우세 / 원정 결정적)으로 나누고
**구간이 실제로 바뀐 순간**만 잡는다.

```
[균형 깨짐]    3회초 2-0   접전 → 원정 우세      50.3% → 26.1%
              결정적이었던 플레이: 김건희 : 삼진 아웃 (-14.8%p)
[승부 기울어짐] 6회말 4-2   접전 → 원정 결정적    40.6% → 12.7%
[주도권 교체]   9회말 7-8   원정 결정적 → 홈 결정적 12.7% → 95.5%
              결정적이었던 플레이: 3루주자 추재현 : 홈인 (+52.7%p)
```

잡음을 세 겹으로 막는다. **경계 히스테리시스**(0.35 경계에서 오르내릴 때마다 전환이
찍히는 것 방지 — 실측에서 3~5회가 사실상 한 국면인데 전환 4건이 잡혔다),
**유지 조건**, **최소 변화량**. 9건 → 4건으로 정리됐다.

경기 막판에는 남은 이벤트가 유지 조건보다 적다. 이걸 빠뜨리면
**끝내기 역전 같은 최대 전환점이 통째로 누락된다.**
